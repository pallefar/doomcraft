17. (replaces the broken 5 and 6.) V4b changes both the CONTENT of
    `content/items.json` (two new rows) and the SERIALIZATION of every item
    line (the new `variantId` column). Either alone moves items@1's fingerprint
    and digest, so they are not separable and no version bump avoids it:
    `itemsAt(1)` recomputes both from the file with whatever code is running.

    The plan therefore does NOT claim the change is compatible. It claims the
    change strands nothing ON THIS HOST TODAY, and pins the mechanism:
    (a) the live origin reports revision 0 with `pending: null` and
        `unsatisfied: []`, so no stored release document records an items
        digest that this change would invalidate;
    (b) a regression test asserts the failure you demonstrated — a release
        recorded against the OLD items digest makes `unsatisfied()` return
        exactly `["items@1"]` — so the mechanism is asserted in the suite
        rather than assumed in a comment;
    (c) the deploy order is: ship the binary and the content together, since
        both sides of the digest move in the same commit.

18. The genuinely dangerous half of what you found is not the 409. A 409 is
    loud. It is that `resolveFor()` returns revision **0** instead of the
    pinned revision **2** with no error to the caller — a host quietly serving
    different content than the release document names. V4b does NOT fix that:
    it is a release-service change with its own blast radius, it is not needed
    for the ownership token, and bundling it would put a second reason-to-fail
    inside a phase whose whole point is being small enough to judge. It is
    recorded as a separate finding with your reproduction attached.
    QUESTION FOR YOU: is deferring it the wrong call — i.e. does any sequence
    reachable in V4b itself make that silent fallback fire?

19. `rollMatchDrops` (server/src/packs.ts) gains `ItemKind.WEAPON_VARIANT` to
    the kinds it skips, beside TITLE and TROPHY. The regression test uses your
    seeded draws: against a manifest containing `weapon_variant-shotgun-slug`,
    `rand` yielding `[0, 0.6, 0.6]` returns

    return `[]`, or a non-variant ref, on the fixed code. The test is proven
    red by reverting the one-line exclusion, and what goes red is checked to be
    that assertion and not a different one.

20. With clause 19 in place, variant supply in V4b is zero by three
    independent mechanisms, each asserted separately rather than argued:
    `CRAFTABLE_KINDS` has no WEAPON_VARIANT so no craft mints one;
    `rollMatchDrops` skips the kind so no match drops one; and trading moves
    existing copies without creating any. There is no other grant path in
    V4b's scope. V4e adds the entry recipe that deliberately breaks this.

21. (new — the live defect your review surfaced.) `KIND_BY_NAME` and
    `RARITY_BY_NAME` are looked up with `MAP[str]`, which finds inherited
    `Object.prototype` members, so `kind:"constructor"` yields a FUNCTION that
    is not `undefined` and passes the guard. Both lookups move to
    `Object.hasOwn(MAP, str) ? MAP[str] : undefined`, the same fix commit
    `8c6f196` applied to `BANDS.toString` in the variants parser. Proven red
    two ways: the manifest must be REFUSED, and the digest collision between
    `kind:"constructor"` and `kind:"toString"` must be gone. This is a fix to
    shipped code and it rides in V4b because V4b is already rewriting this
    parser; it is called out in its own commit message.

22. Clause 7's parse-time byte cap is doing more work than the original plan
    credited it with: the true ceiling is 434 bytes, not 254, because `name`
    and `text` are capped in UTF-16 CODE UNITS (`.slice(48)`, `.slice(24)`)
    while the pack cap is in UTF-8 BYTES, so a CJK name costs three bytes per
    unit. The cap must therefore be measured in UTF-8 bytes — the same
    `utf8Bytes` helper `parseChallengesManifest` already uses — and NOT in
    `.length`. A `.length` check would pass a 434-byte line as 96.
